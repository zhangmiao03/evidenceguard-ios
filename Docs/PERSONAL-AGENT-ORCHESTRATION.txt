anker 主对话与 personal agent 编排
2026-10-16

本次结论

build 11 分发了已完成的早晚设置、SDK 宿主修复和调试入口调整，主动消息主对话改造没有包含。当时源码已有“普通 run + 主动消息”的局部展示，但助手首页仍会恢复上次独立话题，历史模式隐藏主动消息，推送又优先打开证据，因此不能算完成主对话闭环。

本次已完成的开发

1. 助手首页固定为原有 anker 主对话，独立话题作为可返回的页面打开。保留原会话 ID、草稿、待确认发送请求和独立话题内容。
2. 主对话将现场问答、历史问答、主动消息及早晚报告按时间排列。用户问题和助手回复分别排序，新完成的回复使用 completedAt；旧记录缺失该时间时沿用原轮次时间，不伪造历史时间。稳定 ID 去重，同一主动消息的合并更新仍是同一行。
3. 主动消息正文直接显示，来源和证据按需展开；可直接引用回复。切换到历史模式不会隐藏主动消息，引用回复切回现场与守护模式，原历史草稿保留。
4. 主对话上下文可衔接两种模式的最近问答；独立话题和其他安装身份的问答不混入。历史查询仍按摄像头范围筛选历史上下文，冻结的只读工具权限不变。
5. 主动消息推送优先返回主对话并定位 messageId；提醒记录也提供同一入口。来源证据仍可从消息内单独打开。GET /api/personal/messages/{id} 按客户端归属读取，旧推送和引用不再受 bootstrap 最近 50 条窗口限制。
6. 主对话可见区域内的消息标记已读；打开后台页面、仅预取数据不会消费未读。处理、稍后提醒等反馈保持原策略。切换服务时清理打开的消息缓存，并拒绝上一服务迟到的消息与 bootstrap 响应。

编排现状：从观察到用户看到消息

摄像头事件 / 已授权定时观察 / 守护结果 / 用户订阅的早晚时段
  → 持久事实与观察回执
  → proactive_jobs 候选任务及去重键
  → 程序检查来源、有效期、订阅、免打扰、处理状态和频率
  → Codex App Server 驱动豆包与限定的只读工具
  → 程序校验结构、来源及生成期间事实是否变化
  → assistant_messages 持久消息 + 兼容的 personal_inbox
  → anker 主对话
  → 可选 push_outbox → APNs → 手机点入同一消息
  → 用户已读、处理、延后或回复 → 保存反馈，影响后续检查

消息与推送是两个对象。消息保存后就应在主对话可见；关闭系统推送不应让已有消息消失。APNs accepted 只表示 Apple 接受，不能当作手机已经展示或用户已读。

对应你提供材料中的六个环节

一、观察
已有官方 SDK 事件接收、摄像头取样/核验、守护事件、只读连接器，以及用户主动共享的手机日历/提醒事项快照。连接器读取与后台主动订阅不是同一能力；不能声称现有邮件、日历已持续自动感知所有变化。真实硬件链路仍需独立验收。
代码：Cloud/server/evidenceguard/camera/ingest.py、camera/watch.py、connectors.py、personal.py。

二、状态
SQLite 保存 runs、events、personal_memories、memory_jobs、proactive_jobs、assistant_messages、personal_inbox、push_outbox；设备动作有自己的确认与回执。独立话题不会重新绑定 personal_conversations 中的主对话。
代码：store.py、conversations.py、memory.py、proactive.py、push.py。

三、本轮上下文
当前工具清单在运行开始时冻结。输入包括有效记忆、偏好、当前任务事实、本会话最近最多 16 轮且总计 18,000 字符预算的完整问答对；主对话另附最近 8 条主动消息，显式引用附原消息及来源。本次把主对话的现场/历史文本接续起来，仍限制历史模式的摄像头上下文。
记忆采用豆包提取用户明确说过的事实、原话、有效期、替代关系，并支持删除抑制。现状是把有效记忆加入上下文，尚不是按当前问题检索、排序、压缩的大规模记忆系统。原始聊天、持久记忆和本轮上下文仍是不同层。
代码：harness/contract.py、harness/runtime.py、app.py、personal.py、memory.py。

四、决策
主动检查主循环每 10 秒运行一次，规则先筛候选；不是每 10 秒无条件调用模型。普通候选低于 50 分保持安静，50–79 分进入摘要候选，80 分及以上才考虑发消息，发布前仍要重新核验。普通消息最多每日 6 条、至少间隔 5 分钟，同类事件短期内可合并。早晚报告是用户订阅，按本地日期和早/晚时段去重，不受普通价值评分和 6 条额度限制；事实正文由程序模板生成，模型主要筛选/排序，只能依据已保存记录。
代码：proactive.py、briefings.py。

五、执行
最近部署记录中的手机执行器是官方 Codex App Server 0.162.1 + doubao-seed-2-1-lite-260915。每次运行启动独立临时线程和进程，Codex 驱动模型与工具循环，Python 宿主负责参数、作用域、确认和实际回执。聊天通常最多 8 步，主动评估最多 4 步。普通聊天时限 180 秒、历史查询 420 秒。现有手机服务一次只运行一个 Codex 进程；内存中的分通道队列还承担排队限制。
摄像头、工具、视觉、embedding 仍沿用既定豆包方案，本次没有换模型或开放 shell、网页、子 agent。创建草案不等于启用任务；主动评估只读，不自行控制设备。
代码：harness/codex.py、harness/runtime.py、harness/scheduler.py、harness/tools.py。部署背景见 CODEX-CLOUD.md。

六、连续性
主动候选、记忆提取和推送有持久任务、状态与重试，消息发布有唯一键。进程重启可以重新评估只读候选，不能据此声称所有长任务都可续跑。普通运行在重启后标记 interrupted；当前 scheduler 是进程内 asyncio 队列，没有通用的步骤检查点、租约领取/续租、跨进程接管机制，也不会盲目重放设备副作用。

下一阶段建议（尚未实现）

先把一个跨时间任务做完整：明确用户目标 → 订阅一个有授权的数据源 → 保存来源版本与变化 → 更新候选 → 决定行动或等待 → 记录授权与动作结果 → 到期复查或完成。需要补的是通用 tasks/runs/steps、next_check_at、幂等动作回执和重启恢复，再扩展邮件/日历的变化订阅及按相关性挑选记忆。优先用“该提醒 / 应保持安静 / 已取消不再提醒 / 重启不重复执行”的固定用例验证。

你提供的 Today/OpenMuse 材料用于以上六层分析框架和差距对照；本次没有重新审计 Today 私有后端或验证 OpenMuse 的线上表现，也没有把附件中的建议作为部署指令。
