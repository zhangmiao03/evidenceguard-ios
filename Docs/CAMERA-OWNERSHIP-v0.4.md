# v0.4：实时摄像头独占与历史回顾

日期：2026-09-22。此版本继续使用原生 SwiftUI App，摄像头为双路本地合成测试源。

## 已实现的行为

1. AI 输入区选择“实时守护 / 历史回顾”。两种模式使用独立对话记录和输入草稿；切换模式不取消另一模式已经提交的运行。
2. 一台摄像头可保存多个草案，但只允许一个 active Skill。不同摄像头可各自守护；双摄任务原子占用两台。
3. 创建草案不抢占设备。编辑页显示当前占用任务；启用冲突时先保存草案，再提示“保留草案，不切换”或“暂停原任务并启用此任务”。
4. 恢复暂停任务也检查占用。确认切换会暂停占用任务并释放其全部摄像头；规则修改草案确认后按原有语义停止其旧版本。
5. App 提交占用任务 ID 与 executionEpoch，旧确认不能暂停一个后来恢复或替换的执行实例。任意冲突变化都要求重新确认。
6. 暂停、停止和一次性完成释放设备。恢复后重新建立观察基线，不把暂停前后画面拼成一次离区事件；旧告警与已有证据保留。
7. 一般助手请求新画面沿用当前 owner，按设备串行操作，不切换任务。暂停任务中的实时工具调用被拒绝。
8. 历史模式只注册证据检索与已保存图片读取工具，即使模型主动请求实时取图、复核、草案生成也无法执行。相对日期由服务器按 Asia/Shanghai 计算，记录计数由服务器返回。
9. 历史结果说明可用证据范围及截断情况。当前是离散图片和事件，没有连续录像覆盖。`inside/outside` 表示位置，不能直接解释成进入/离开动作。

## 后端边界

- Store：SQLite 即时写事务串行化冲突检查与状态变更；active 状态是持久化所有权的依据。启动时发现旧版重复占用，会暂停全部冲突任务并写入恢复事件，不任意挑选胜者。
- CameraService：按设备加锁，切换等待在途调用结束；取图进入队列时记住 epoch，在执行前及回执处理时重新校验。
- ObservationWorker：拒绝旧执行实例的状态写入；任务切换后旧计算不能恢复旧 owner。
- Harness：延续 MiiMiao v1.0 对照的 TaskEnvelope、工具注册表、Provider 与持久事件边界。新增 history lane，并发上限 2；实时 chat lane 为 3。没有移植完整 MiiMiao Runtime。
- SDK：两款 Adapter 可注入 OfficialSDKBridge，RoutedCameraAdapter 按 cam-a/cam-b 路由，主动请求带所有权上下文；厂商函数与协议不作猜测。详见 [SDK 合同](../Cloud/CAMERA-SDK-CONTRACT.md)。

## 验证

- 服务端自动测试：40 项通过，包括争抢单摄像头、两台独立执行、双摄切换原子性、旧确认失效、恢复基线、旧 Worker 写入阻断、在途请求排空、旧排队请求拒绝、历史读取隔离、并行分析、两款 SDK 端口路由、相对日期计算与 API 冲突回执。
- 原生 Xcode Simulator 构建通过。
- 模拟器检查：历史模式隐藏实时预览/取图操作，文字输入仍可用；原有双摄任务继续运行。启用冲突弹窗显示占用任务；选择“保留草案，不切换”后，验证原任务仍 active、executionEpoch 未变，新任务仍 draft。验证草案已清理。
- 真实 DeepSeek 历史回顾复测完成，仅调用 `search_evidence`，没有取新画面、生成草案或更改守护。返回 15 条已存记录（区域内 9、区域外 3、无法判断 3），模型日期与计数按服务端提供的结果解释。首次复测发现的日期换算错误已通过相对日期参数及服务器计数修正。

## 尚未覆盖

本地服务按单进程运行。多进程/多副本部署需要将设备锁升级为可续期的分布式租约与硬件侧 fencing。真实 T8171/T8214 SDK、持续拉流停止回执、PTZ、历史录像导入、通用目标识别及公网鉴权仍未验收。本次完成 SDK 接口与业务约束，不等于已连接两台真机。
